# Project Bootstrap — быстрый старт

**Версия Plugin:** 0.1.5
**Разработчик:** Gipsy
**Статус:** beta

## Что это

**Project Bootstrap** помогает организовать работу над проектом так, чтобы она не зависела от одного чата, одной машины или памяти пользователя.

Plugin разделяет работу на три роли:

- **Manager** — помогает понять и настроить проект: цель, способ работы, среды, Git, переносимость, права и передачу управления в рабочую среду.
- **Master** — координирует уже настроенный проект: сверяет актуальное состояние, разбивает работу на задачи, принимает результаты и следит за целостностью проекта.
- **Task** — выполняет одну ограниченную задачу: реализацию, исследование, отладку, проверку или восстановление после прерывания.

Cloud Manager — не четвёртая роль. Это тот же canonical Manager contract, сгенерированный в один файл для ChatGPT Project.

В Plugin-capable среде оставьте все три компонента включёнными. Это не три ручных режима: Plugin должен выбирать подходящую роль по смыслу запроса.

## Два способа начать

### Cloud-first: ChatGPT Project

Подходит, если вы хотите начать с обсуждения цели, discovery и project-level решений в ChatGPT Plus.

Один раз для Project:

1. Создайте ChatGPT Project.
2. Скачайте [CHATGPT_CLOUD_MANAGER.md](CHATGPT_CLOUD_MANAGER.md) из опубликованной версии Project Bootstrap.
3. Добавьте этот файл как источник Project.
4. Скопируйте только короткий activation stub из раздела **Project Instructions** в настройки Project.
5. Начните описывать проект обычными словами на своём языке.

Полный artifact в Project Instructions копировать не нужно. Загружать остальные internal contracts тоже не нужно. При обновлении Project Bootstrap замените старый artifact новым из опубликованной версии.

### Codex-first: установленный Plugin

Если работа уже начинается в реальном workspace, используйте установленный Project Bootstrap Plugin. Оставьте Manager, Master и Task включёнными и опишите проект или задачу обычными словами.

Наличие Cloud-first пути не делает его обязательным. Выбирайте среду по необходимым evidence и действиям.

## Как начать разговор

Для нового проекта:

> Хочу создать новый проект для разработки сайта.

Для существующего проекта:

> У меня уже есть проект. Помоги подключить его к Project Bootstrap и организовать дальнейшую работу.

Для продолжения:

> Продолжим работу над проектом.

Для конкретной задачи:

> Нужно добавить авторизацию.

Для бага:

> Есть баг: после сохранения форма иногда сбрасывается. Разберись и исправь.

Для проверки:

> Проверь, всё ли готово и ничего ли мы не упустили.

Специальные команды и знание внутренних терминов обычно не нужны.

## Как устроены роли

### Manager

Manager — верхний уровень управления проектом. Он используется при старте нового проекта, подключении существующего, крупной перестройке, переносе, восстановлении или изменении общей схемы работы.

Он может уточнить назначение проекта, уровень участия пользователя, рабочие среды, Git, переносимость, migration и разрешения.

Если для решения нужно проверить реальные файлы, Git или сервер, а Manager не имеет к ним доступа, он не должен придумывать состояние. Вместо этого он подготовит ограниченный prompt для Codex.

### Master

Master — координатор уже настроенного проекта.

Он читает актуальное проектное состояние, сверяет его с реальными файлами/Git/средой, определяет следующую работу, создаёт отдельные Task только когда это действительно нужно и принимает их результаты.

Маленькую работу Master может выполнить сам: отдельная Task нужна не всегда.

### Task

Task — исполнитель одной конкретной работы.

У Task должны быть понятны цель, границы, разрешённые действия, ограничения и критерии готовности.

Task не должен самовольно менять общую архитектуру проекта. После работы он проверяет фактический результат и возвращает его Master.

## Насколько вы хотите участвовать

Manager предлагает три режима:

- **Совместно** — чаще показывать существенные варианты и обсуждать решения.
- **По ключевым решениям** — разумный режим по умолчанию: агент делает рутинную работу сам, а вас подключает к важным развилкам.
- **Делегированно** — максимум самостоятельной работы с безопасными обратимыми решениями в уже разрешённых границах.

Режим участия не выдаёт дополнительных прав. Например, право менять файлы не означает автоматически право публиковать изменения или развёртывать production.

## Переход из Cloud ChatGPT в Codex

Manager предлагает переход только тогда, когда нужны реальные workspace evidence или действия.

Есть два варианта:

- **Native path** — в Codex установлен Project Bootstrap Plugin. Cloud Manager даёт короткий invocation wrapper и canonical Manager → Master handoff.
- **Fallback path** — обычная Codex session без Plugin/Skills. Cloud Manager даёт bounded prompt только для принятой проверки или работы, не копируя весь Project Bootstrap.

После возврата Codex Manager проверяет evidence и объясняет результат пользователю на его языке. Английский Codex prompt или return не должен переключать весь видимый ответ на английский.

## Язык общения

Пользовательские объяснения, вопросы, review, выводы и интерпретация результатов остаются на текущем языке пользователя.

Внутренние prompts между AI-сессиями могут быть на английском — это нормально. Язык видимого общения меняется только по просьбе пользователя.

## Чаты можно менять

Главный принцип:

> **Sessions are disposable. Project/task state is durable.**

Проект не должен зависеть от одного длинного чата. Если задачу нужно продолжить позже, важное текущее состояние сохраняется в проектных файлах или других согласованных источниках.

Отдельный Project Decision Snapshot в ChatGPT не обязателен. Он нужен только когда уже накопились существенные project-level решения, им надо пережить смену cloud session и более подходящего canonical workspace state ещё нет.

## Не вся работа требует сложного процесса

Project Bootstrap должен быть адаптивным:

- нет отдельной задачи → не создавать Task ради формальности;
- задача маленькая → Master может сделать её сам;
- задача короткая → не нужен ExecPlan;
- не нужна изоляция → не нужен отдельный Git branch/worktree;
- не нужен перенос между средами → не нужен PORTABLE workflow;
- не нужна migration → не нужны migration-артефакты;
- короткий discovery → не нужен Decision Snapshot.

Идея Plugin — **уменьшать**, а не увеличивать операционную сложность.
