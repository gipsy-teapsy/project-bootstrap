# Project Bootstrap — руководство пользователя

**Версия Plugin:** 0.1.3
**Разработчик:** Gipsy
**Статус:** beta

## 1. Зачем нужен Project Bootstrap

Project Bootstrap организует **сам способ работы над проектом** в ChatGPT, Codex и других агентных средах.

Его задача — сделать проект понятным, продолжимым и управляемым:

- не зависеть от одного длинного чата;
- не заставлять пользователя помнить всё состояние проекта;
- отделять общие проектные решения от конкретной работы;
- продолжать незавершённые задачи после пауз и смены сессии;
- не путать локальные файлы, Git, серверы и другие среды;
- проверять не только то, что «тесты зелёные», но и то, что принятая цель действительно достигнута;
- не создавать лишний workflow там, где достаточно простого действия.

Project Bootstrap не является отдельной CMS, task tracker или Git-клиентом. Он работает поверх тех файлов, репозиториев, сервисов и сред, которые реально нужны конкретному проекту.

Текущая архитектура Plugin состоит из трёх пользовательских Skills и общего Shared Core:

```text
Manager → Master → Task → Verify → Converge → Handoff → Master Review
```

При этом пользователь обычно не обязан управлять этой схемой вручную.

---

## 2. Что означают три компонента Plugin

После установки в настройках Plugin видны три компонента:

- `project-bootstrap-manager`
- `project-bootstrap-master`
- `project-bootstrap-task`

В обычной работе **оставьте включёнными все три**.

Это не три «режима», которые пользователь обязан переключать вручную. Это три роли одной системы. Запрос должен маршрутизироваться в подходящую роль по смыслу.

Если вы пишете:

> Хочу создать новый проект.

это работа Manager.

Если проект уже настроен и вы пишете:

> Продолжим работу.

это обычно работа Master.

Если требуется отдельная ограниченная работа:

> Исправь баг сохранения формы.

Master может выполнить её сам, если она действительно мала, либо выделить отдельную Task.

---

## 3. Manager — control plane проекта

Manager — верхний уровень Project Bootstrap.

Он используется, когда нужно:

- начать новый проект;
- подключить существующий;
- разобраться, как проект должен быть организован;
- восстановить проект после значительного расхождения;
- перестроить схему работы;
- спланировать migration;
- определить работу между несколькими средами;
- изменить project-level правила.

### Что делает Manager

Manager кратко ориентирует пользователя и определяет состояние проекта:

- **NEW** — проект создаётся;
- **EXISTING** — проект уже существует, но ещё не подготовлен под текущую модель;
- **PREPARED** — проект уже имеет достаточное durable state и структуру;
- **UNKNOWN** — пока не хватает данных.

Дальше он устанавливает только необходимые project-level вещи:

- назначение проекта;
- режим участия пользователя;
- значимые архитектурные решения;
- Environment Map;
- Git-стратегию;
- потребность в PORTABLE;
- потребность в migration;
- project-level authority;
- рекомендуемый execution profile.

Manager не должен превращать старт проекта в универсальную анкету. Если факт можно получить из доступных файлов, документации, Git или другой проверяемой среды, пользователь не должен вспоминать его вручную.

### Ограничение Manager

Manager не должен утверждать, что знает текущее состояние файлов, Git, сервера, базы данных или другой изменяемой системы, если фактически это не проверял.

Если Manager работает в ChatGPT и для решения нужен inspect реального workspace, он должен:

1. объяснить, какую информацию нужно получить;
2. подготовить ограниченный prompt для Codex/другой рабочей среды;
3. получить результат;
4. интерпретировать его для пользователя.

Manager — не просто генератор prompt. Он остаётся интерфейсом управления проектом до передачи операционной координации Master.

---

## 4. Master — координатор рабочего проекта

Master работает с уже bootstrapped-проектом.

Его задача — держать актуальную project-wide картину и управлять реальной работой.

Master:

- читает durable project state;
- проверяет фактический workspace перед доверием изменяемым данным;
- сверяет project records с Git, файлами и релевантными live systems;
- понимает, какие логические задачи активны;
- маршрутизирует новую работу;
- создаёт Task только когда это оправдано;
- принимает checkpoints и handoffs;
- управляет продвижением нового знания в project state;
- выполняет финальный Master Review;
- проверяет project-level convergence.

### Master не равен одному чату

Важно различать:

- **Master** — логическая роль и актуальное состояние координации;
- **Master Session** — конкретный чат/сеанс, который сейчас выполняет эту роль.

Старый Master Chat не является вечным источником истины.

Если проект изменился после последней сессии, новый или вернувшийся Master должен сначала обновить своё представление из durable state и фактической среды.

### Маленькие задачи

Не каждая работа требует отдельной Task.

В текущем control model прямо предусмотрено:

> A small task may be executed directly.

То есть если работа небольшая, локальная и не требует отдельной continuity/ownership boundary, Master может сделать её сам.

---

## 5. Task — ограниченный исполнитель

Task выполняет одну логическую работу внутри проекта.

Это может быть:

- реализация функции;
- исправление бага;
- исследование;
- проверка;
- настройка среды;
- работа с файлами;
- работа с Git;
- recovery конкретной задачи.

Task получает **Task Delta** — только то, что отличается для этой конкретной работы.

Обычно в нём задаются:

- Goal;
- Scope;
- Context;
- Authority;
- Constraints;
- Done when;
- Evidence.

Task не должен:

- самостоятельно менять project-wide архитектуру;
- расширять scope без причины;
- менять область другой Task без authority;
- превращаться во второго writer той же логической задачи.

Безопасный default:

> **ONE LOGICAL TASK → ONE ACTIVE WRITER AT A TIME.**

## 6. Пользователю не нужно вручную выбирать Manager / Master / Task

Главный UX Project Bootstrap — естественный язык.

Примеры:

> Хочу создать новый проект для разработки сайта.

> У меня уже есть проект. Подключи его к Project Bootstrap.

> Продолжим работу.

> Нужно добавить авторизацию.

> Есть баг: иногда теряется сохранённое значение.

> Проверь, всё ли готово.

> Вчера работа оборвалась, восстанови состояние и продолжим.

> Завтра продолжу с другого компьютера.

Plugin должен сам понять, нужен ли Manager, Master, Task, recovery, verification или другой внутренний маршрут.

Явное знание названий Skills полезно для диагностики и разработки самого Plugin, но не должно быть обязательным условием обычной работы.

## 7. Participation — сколько решений пользователь хочет видеть

Manager предлагает три project-level режима.

### Совместно — `COLLABORATIVE`

Агент сам исследует проект, но чаще показывает существенные находки, реальные альтернативы и последствия.

Подходит, если вы хотите глубоко участвовать в устройстве проекта и понимать принимаемые решения.

### По ключевым решениям — `ESSENTIAL`

Разумный default.

Агент самостоятельно исследует и готовит рекомендуемый путь. Пользователь подключается там, где:

- выбор существенно влияет на проект;
- есть несколько действительно разных вариантов;
- требуется новое разрешение;
- возник blocker.

### Делегированно — `DELEGATED`

Агент самостоятельно принимает безопасные обратимые решения в пределах уже предоставленных прав.

К пользователю он обращается, когда нужны:

- решение с существенными последствиями;
- дополнительный ресурс;
- новое permission;
- действие с повышенным риском.

### Participation не равно permission

Даже `DELEGATED` не означает автоматическое право:

- публиковать Git-изменения;
- создавать credentials;
- делать deployment;
- менять production;
- удалять важные данные.

Режим участия определяет частоту вовлечения пользователя, а не уровень безопасности и не технические права.

## 8. ChatGPT и Codex: Cloud-first и Codex-first

Роль Project Bootstrap не привязана жёстко к устройству или продукту. Выбор стартовой среды определяется тем, где удобнее принять решения и где доступны необходимые evidence и действия.

### Cloud-first

Cloud-first подходит, если проект начинается с discovery, обсуждения цели, Participation и project-level решений в ChatGPT Plus.

Cloud Manager — не четвёртая роль и не отдельный Cloud Skill. Это canonical Manager contract, доставленный в ChatGPT Project через сгенерированный [CHATGPT_CLOUD_MANAGER.md](CHATGPT_CLOUD_MANAGER.md).

При создании ChatGPT Project пользователь один раз:

1. создаёт ChatGPT Project;
2. скачивает [CHATGPT_CLOUD_MANAGER.md](CHATGPT_CLOUD_MANAGER.md) из опубликованной версии Project Bootstrap;
3. добавляет этот файл как источник Project;
4. копирует только короткий activation stub из раздела **Project Instructions** в настройки Project;
5. начинает описывать проект обычным запросом на своём языке.

Загружать Manager Skill, Shared Core и templates отдельными файлами не нужно: они уже механически собраны в artifact с provenance. Полный artifact в Project Instructions не копируется. При обновлении Project Bootstrap старый artifact удаляется и заменяется новым.

Cloud ChatGPT хорошо подходит для:

- Manager-обсуждения;
- discovery;
- принятия project-level решений;
- объяснения вариантов;
- подготовки handoff в рабочую среду;
- интерпретации результата Codex для пользователя.

### Codex-first

Codex-first подходит, если работа сразу начинается в реальном workspace. В среде с установленным Project Bootstrap Plugin оставьте Manager, Master и Task включёнными и сформулируйте запрос естественным языком.

Codex или другая workspace-среда нужна, когда требуется:

- читать реальные локальные файлы;
- запускать команды;
- проверять Git;
- менять код;
- запускать тесты;
- работать с сервером или другими инструментами.

Cloud-first — рекомендация для удобного discovery, а не обязательный control path. Наличие capability не означает, что она обязана управлять workflow. Критерий простой: роль должна иметь evidence и authority для требуемых mutable facts и действий.

---

## 9. Cloud Manager → Codex handoff

Cloud Manager предлагает переход в Codex только когда следующий принятый шаг требует workspace evidence или действия. Перед переходом он объясняет пользователю:

- что именно будет проверено или сделано;
- зачем требуется workspace-capable среда;
- какой execution profile уместен;
- какой prompt нужно передать;
- какой evidence должен вернуться.

### Native path

Native path используется только когда в Codex действительно доступны установленный Project Bootstrap Plugin и Skills.

Handoff состоит из двух независимых частей:

1. короткого environment-specific invocation wrapper;
2. canonical Manager → Master handoff body из `manager-to-master.md`.

Wrapper выбирает установленную capability, но не дублирует поля проекта. Структура PROJECT / ARCHITECTURE / ENVIRONMENT MAP / GIT / CONTINUITY / MASTER START поддерживается только в canonical template.

### Fallback path

Fallback path используется для обычной Codex session без Project Bootstrap Plugin/Skills.

Prompt содержит только bounded goal, workspace boundary, принятый контекст, mutable facts для проверки, scope/exclusions, фактическую authority, done conditions, expected evidence и return contract. Он не копирует весь Project Bootstrap и не создаёт внутри prompt вторую реализацию Manager/Master/Task.

После возврата Manager рассматривает отчёт Codex как evidence: отделяет проверенные факты от inference и open items, сверяет его с принятыми решениями и объясняет результат пользователю. Английский Codex return интерпретируется на текущем языке пользователя.

## 10. Язык пользователя и язык внутренних prompts

Canonical interaction contract разделяет два слоя:

> **USER-FACING → user's language**

Пользовательские объяснения, discovery-вопросы, design review, рекомендации, summary и интерпретация результатов остаются на текущем языке пользователя.

> **AGENT-FACING → English by default where appropriate**

Внутренние contracts, prompts между AI-сессиями и Codex-facing handoffs могут использовать английский для стабильности. Англоязычный uploaded artifact, native/fallback prompt или Codex return не должен переключать окружающее пользовательское общение на английский.

Язык видимого ответа меняется, если пользователь явно просит продолжить на другом языке.

## 11. Sessions disposable, state durable

Один из базовых принципов Project Bootstrap:

```text
SESSIONS ARE DISPOSABLE.
PROJECT/TASK STATE IS DURABLE.
```

Чат — временная runtime-сессия.

Если проект должен надёжно продолжаться после:

- закрытия чата;
- смены модели;
- usage limit;
- перехода на другой компьютер;
- запуска новой Task Session;

значимое актуальное состояние должно быть доступно вне истории конкретного разговора.

Отсюда второй принцип:

```text
FILES ARE MEMORY.
FILES = CURRENT MEMORY.
GIT = HISTORY OF MEMORY.
```

Это не означает, что каждый проект обязан иметь Git или специальный набор файлов. Конкретная архитектура подбирается адаптивно.

### Project Decision Snapshot в Cloud

Отдельный snapshot в ChatGPT Project не является обязательной системой состояния. Manager предлагает или создаёт его только когда одновременно выполнены два условия:

- накопились существенные project-level решения, которые должны пережить смену cloud session;
- более подходящего canonical durable workspace state ещё нет.

Snapshot не нужен для короткого discovery, tentative-информации, решений, которые скоро будут перенесены в workspace state, или когда подходящий durable state уже существует. Если snapshot понадобился, он остаётся компактным и временным; после promotion в canonical workspace state его нужно retire или supersede.

## 12. Task Branch не равен Task Session и не равен Git branch

### Task Branch

Логическая задача проекта.

### Task Session

Один конкретный сеанс/чат, который работает над этой задачей.

Одна Task Branch может пройти через несколько Task Session.

### Git branch

Техническая Git-ветка.

Она создаётся только если для задачи действительно нужна изоляция.

```text
Task Branch ≠ Task Session ≠ Git branch
```

---

## 13. Task State, Checkpoint и Handoff

Эти элементы создаются только когда нужны.

### Task State

Минимальное durable состояние незавершённой логической задачи.

Обычно включает:

- цель/статус;
- текущее состояние;
- Completed;
- следующий шаг;
- blockers;
- важные evidence/verification.

Отдельный файл необязателен: Task State может храниться в уже существующем tracker или project-controlled state.

### Checkpoint

Задача ещё не завершена, но текущая Session может закончиться.

Checkpoint фиксирует состояние, достаточное для продолжения позже.

Он не нужен после каждого сообщения.

### Handoff

Task достигла результата, готового к Master Review.

Закрытие чата само по себе не является Handoff.

---

## 14. ExecPlan создаётся не всегда

ExecPlan нужен для длинной, сложной или interruption-prone задачи, когда повторное восстановление контекста было бы дорогим.

Для небольшой задачи ExecPlan — лишняя церемония.

```text
NO LONG TASK → NO EXECPLAN
```

---

## 15. Recovery после паузы или обрыва

Не каждый перерыв требует полного recovery.

### Обычная чистая пауза

Если turn закончился нормально и проект не мог измениться параллельно, работа просто продолжается.

### Возможная частичная mutation

Если процесс/stream/tool оборвался во время изменения файлов, перед новой записью нужно проверить фактическое состояние.

### Новая Session

Если открыта новая Master/Task Session, она восстанавливает логическое состояние из durable sources и актуальной среды.

Recovery не пытается «вспомнить старый чат слово в слово». Он восстанавливает фактическое состояние работы.

Ни один отдельный файл не считается магическим источником истины для всех типов claims.

---

## 16. Verify и Convergence — разные проверки

### Verify

> Работает ли реализованное так, как мы утверждаем?

### Convergence

> Достигнута ли принятая цель и покрыты ли применимые требования?

Поэтому возможна ситуация:

```text
Tests: PASS
Verify: PASS
Convergence: GAP
```

Например, реализованные функции работают, но одно из требований вообще не было сделано.

Handoff готов только после достаточных Verify и Convergence либо после явного сохранения известного ограничения для решения Master/пользователя.

---

## 17. Как Project Bootstrap работает с багами

Базовый маршрут:

```text
Assess → Fix → Verify original symptom → Converge
```

Сначала подтверждается сам симптом настолько, насколько это разумно.

Причина не должна выдаваться за факт без evidence.

После исправления Task проверяет не только новый тест, но и исходный пользовательский симптом или максимально близкую валидную reproduction.

---

## 18. Evidence и достоверность

Project Bootstrap разделяет силу утверждения:

```text
CONFIRMED
OBSERVED
STRONGLY SUPPORTED
INFERRED
UNKNOWN
```

Task может предложить новое знание, но оно не обязано автоматически становиться project-wide истиной.

Master отвечает за reconciliation и принятие актуального project state.

Нет универсального правила «Git всегда важнее документа» или «live state всегда важнее Git». Сначала определяется, какой именно claim проверяется.

---

## 19. Authority: возможность инструмента не равна разрешению пользователя

Project Bootstrap разделяет Git-authority как минимум на:

```text
READ
CHANGE
COMMIT
PUBLISH
INTEGRATE
```

Например:

- наличие SSH-ключа не означает, что push разрешён;
- право менять код не означает право делать deployment;
- connector access не означает разрешение менять внешнюю систему.

Для чувствительных или внешних действий может потребоваться отдельное подтверждение.

---

## 20. Git используется только когда нужен

Git не является обязательной частью Project Bootstrap.

Если он используется, Plugin различает:

- local Git state;
- remote repository/provider;
- connector access;
- host authentication;
- authority на commit/publish/integrate.

Project Bootstrap не должен создавать Git branch/worktree только потому, что это «правильная разработка».

```text
NO ISOLATION NEED → NO GIT BRANCH / WORKTREE
```

---

## 21. PORTABLE — продолжение проекта в другой среде

PORTABLE нужен только если один логический проект должен продолжаться в разных рабочих средах.

Это может быть:

- несколько компьютеров;
- переносимая копия;
- cloud-synced folder;
- NAS/shared storage;
- Git + отдельное knowledge storage;
- общий внешний сервис;
- смешанная схема.

Project Bootstrap интересует не носитель, а вопрос:

> Доступно ли актуальное project/task state в новой среде?

Credentials, private keys, caches, virtual environments и другие machine-local вещи обычно не должны просто копироваться вместе с проектом.

```text
NO PORTABLE NEED → NO PORTABLE WORKFLOW
```

---

## 22. Environment Map

Для сложного проекта Project Bootstrap может поддерживать Environment Map.

В неё включаются только реально значимые среды, например:

- текущий компьютер;
- второй компьютер;
- shared storage;
- development server;
- test/staging;
- production;
- внешний сервис.

Environment Map — внутренняя опора системы. Пользователь не обязан вручную заполнять большую таблицу.

---

## 23. Migration не равна обычной смене компьютера

Если тот же проект просто продолжается в другой среде, обычно нужен resume + reconciliation.

Migration требуется, когда меняется сама canonical storage/authority architecture: есть источник и назначение, меняется canonical workspace, требуется перенос и нужна приёмка нового состояния.

Project Bootstrap не должен создавать migration workflow при каждом изменении локального пути.

---

## 24. Execution profile: модель и thinking

Project Bootstrap может рекомендовать execution profile для новой Master/Task Session.

Рекомендация состоит из:

- модели или класса capability;
- thinking/reasoning level;
- короткой причины.

Принцип:

> использовать минимально достаточный профиль, а не максимальный по умолчанию.

Ориентировочно:

- простая локальная механическая работа → более быстрый профиль, Low–Medium;
- обычная реализация по принятому плану → balanced/capable, Medium;
- архитектура, сложный recovery/reconciliation, тяжёлый debugging, migration/security design, независимый аудит → strongest suitable, High.

Participation и execution profile — разные оси.

---

## 25. Anti-bloat: Project Bootstrap не должен создавать процесс ради процесса

Shared Core текущего Plugin фиксирует:

> **DO NOT ADD A WORKFLOW WHEN A ROUTING RULE IS ENOUGH.**

Практически это означает:

```text
NO TASK → NO TASK BRANCH
NO LONG TASK → NO EXECPLAN
NO ISOLATION NEED → NO GIT BRANCH / WORKTREE
NO RELEASE PROCESS → NO RELEASE CONTRACT
NO MIGRATION → NO MIGRATION ARTIFACTS
NO PORTABLE NEED → NO PORTABLE WORKFLOW
```

Кроме того, Master может выполнить genuinely small work напрямую.

Если для маленькой задачи создаётся длинная цепочка артефактов и подтверждений без реальной необходимости, это противоречит целевой модели Project Bootstrap.

---

## 26. Что пользователь должен и не должен делать вручную

### Обычно нужно

- сформулировать цель;
- ответить на действительно важные вопросы;
- выбрать Participation;
- предоставить доступ или permission там, где это необходимо;
- принять существенное решение, если у вариантов разные последствия.

### Обычно не нужно

- вручную выбирать Manager/Master/Task на каждом шаге;
- знать названия recovery/verify/convergence;
- создавать Task ID;
- писать Task State вручную;
- выбирать Git workflow без причины;
- пересказывать весь прошлый чат после перехода в новую Session;
- помнить внутреннюю терминологию Plugin.

Project Bootstrap должен быть роутером работы, а не системой, которую пользователь вынужден вручную «операторить».

---

## 27. Типовые сценарии

### Новый проект

> Хочу создать новый проект для разработки сайта.

Manager ориентирует, задаёт только необходимые вопросы и формирует project-level setup.

### Существующий проект

> У меня есть существующий проект. Подключи его и сначала разберись в текущем состоянии.

Manager определяет, что уже существует, а mutable workspace facts проверяются в рабочей среде.

### Продолжить работу

> Продолжим проект.

Master обновляет актуальное состояние и определяет следующий шаг.

### Новая функция

> Нужно добавить авторизацию.

Master либо делает маленькую работу сам, либо создаёт bounded Task.

### Баг

> После сохранения иногда исчезает выбранный язык.

Task следует маршруту Assess → Fix → Verify original symptom → Converge.

### После обрыва

> Работа оборвалась во время изменений. Проверь фактическое состояние и продолжим.

Выполняется bounded recovery до новой mutation.

### Новый компьютер

> Хочу продолжить этот проект на домашнем компьютере.

Project Bootstrap проверяет portable/continuity architecture и не предполагает, что перенос локального чата обязателен.

### Проверка готовности

> Проверь, всё ли готово.

Система должна проверить не только отдельные тесты, но и convergence с принятой целью.

---

## 28. Если Plugin ведёт себя не так, как ожидалось

### Plugin задаёт вопросы, ответы на которые уже есть

Скажите:

> Сначала используй доступные файлы и текущее состояние проекта; спрашивай меня только о действительно неизвестных решениях.

### Plugin пытается угадать состояние локального workspace из Cloud ChatGPT

Скажите:

> Не предполагай mutable workspace facts. Подготовь bounded inspection prompt для Codex.

### Plugin создаёт слишком много процесса для мелкой задачи

Скажите:

> Это bounded/light изменение. Используй минимально необходимый workflow и не создавай отдельные артефакты без необходимости.

Это соответствует текущему anti-bloat принципу Plugin.

### Нужно явно вернуть уровень Manager

Скажите:

> Нужна project-level переоценка архитектуры/сред/authority, а не выполнение отдельной задачи.

### Нужно продолжить конкретную Task

> Продолжим вчерашнюю задачу по авторизации. Сначала обнови её фактическое состояние.

## 29. Beta-статус

Project Bootstrap v0.1.3 — beta.

Cloud Manager прошёл начальное ручное smoke testing; расширенное behavioral testing продолжается в beta. Это не означает, что весь документированный набор Cloud-сценариев уже выполнен.

Валидная структура Plugin и manifests не равны полному behavioral lifecycle testing.

Особенно полезно фиксировать реальные случаи, где:

- выбран неправильный уровень Manager/Master/Task;
- возник лишний workflow;
- пользователь вынужден знать внутреннюю терминологию;
- recovery повторяет уже выполненную работу;
- verification заявлена без свежего evidence;
- Task расширяет scope;
- authority спрашивается слишком часто или, наоборот, недостаточно.

Такие случаи — материал для следующей доработки Plugin.

---

## 30. Главное

У Project Bootstrap есть глубокая внутренняя модель, но пользовательский интерфейс должен оставаться простым.

В нормальной работе достаточно говорить:

> «Создадим проект.»

> «Продолжим.»

> «Есть баг.»

> «Нужно добавить функцию.»

> «Работа оборвалась.»

> «Завтра продолжу на другом компьютере.»

> «Проверь, всё ли готово.»

Внутри Plugin сам должен решить, нужен ли Manager, Master, Task, recovery, verification, handoff или другой механизм.

Главный критерий успеха:

> **Project Bootstrap должен уменьшать стоимость управления проектом, а не добавлять новую операционную сложность.**
