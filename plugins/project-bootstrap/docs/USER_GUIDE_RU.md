# Project Bootstrap — руководство пользователя

**Версия:** 0.1.8 · **Разработчик:** Gipsy · **Статус:** бета

Project Bootstrap помогает организовать работу над проектом в ChatGPT, Codex и других средах, где помощник может выполнять задачи. Вы описываете цель обычными словами; система помогает выбрать следующий шаг, выполнить работу, проверить её и сохранить то, что потребуется для продолжения.

Для первого запуска используйте [быстрый старт](QUICK_START_RU.md). Здесь подробно объясняется, как система должна вести себя в разных ситуациях. Руководство можно читать целиком или использовать как справочник: сначала смысл механизма и пример, затем — внутреннее название, если оно может встретиться в отчёте.

## 1. Знакомство и начало работы

### 1.1. Назначение и границы

Проблема долгой работы с помощником — решения и состояние часто остаются внутри одного разговора. После паузы приходится вспоминать, что уже сделано, где находятся файлы, какой вариант приняли и что было запрещено менять. Project Bootstrap помогает отделить проект от истории конкретного чата.

Он организует три вида работы: настройку проекта, координацию дальнейших шагов и выполнение отдельных задач. Для проекта выбирается подходящий способ хранения важных решений и состояния. При продолжении система сверяется с этими записями и с реальными рабочими ресурсами.

Например, для сайта уже согласованы назначение, способ записи клиентов и запрет менять действующий сервер. Эти сведения должны оставаться доступными, даже если разработка продолжается в новом чате. Однако запись «тесты прошли вчера» не доказывает, что они проходят после сегодняшних изменений.

Project Bootstrap работает поверх ваших файлов, репозиториев и сервисов. Он не заменяет сам редактор, Git, систему учёта задач или сервер. Установка плагина также не даёт помощнику доступ ко всем ресурсам и не гарантирует правильность любой реализации: результат нужно проверять в подходящей среде.

Масштаб организации зависит от работы. Для правки одного документа достаточно нескольких действий и короткого результата. Для долгого проекта полезны сохранённые решения, планы и состояние незавершённых задач. Сложность появляется ради продолжения и проверки, а не ради обязательного набора документов.

### 1.2. Начало работы

Есть три практических варианта подключения:

| Вариант | Когда удобен | Что подключить |
| --- | --- | --- |
| Обычный чат ChatGPT | Один разговор, обсуждение идеи, пробный запуск | Прикрепить [CHATGPT_CLOUD_MANAGER.md](CHATGPT_CLOUD_MANAGER.md) и попросить использовать его как инструкции Project Bootstrap. |
| ChatGPT Project | Долгая работа в нескольких связанных чатах | Добавить тот же файл в источники и вставить короткую инструкцию в Project Instructions. |
| Codex с установленным плагином | Работа с реальными файлами и инструментами | Установить Project Bootstrap, оставить три компонента включёнными и открыть папку рабочего проекта. |

Пошаговые действия и готовый полный блок Project Instructions есть в [быстром старте](QUICK_START_RU.md). Для рабочего пространства ChatGPT с установкой через GitHub используется [инструкция установки](https://github.com/gipsy-teapsy/project-bootstrap/blob/main/docs/MARKETPLACE_INSTALL_RU.md). Доступность установки зависит от среды и правил организации; способ с файлом для ChatGPT существует отдельно от установки плагина.

Первое сообщение должно описывать цель, а не внутреннюю роль:

> Хочу сделать приложение для семейных расходов. Помоги уточнить, что оно должно делать, и организовать работу.

Или:

> У меня уже есть сайт. Подключи Project Bootstrap и сначала разберись в его текущем состоянии.

Если у вас есть важное ограничение, добавьте его сразу: «Пока ничего не меняй», «Не трогай действующий сервер» или «Сначала нужен только план». Система должна учитывать такие ограничения на следующих шагах и при переходе между средами.

ChatGPT удобен для обсуждения цели, вариантов, принятия решений и объяснения результатов. Codex нужен, когда следующий шаг требует читать или менять реальные файлы, проверять Git, запускать команды и тесты. Начинать с ChatGPT необязательно; можно вести проект целиком в Codex.

### 1.3. Новый и существующий проект

#### Если проект только начинается

Project Bootstrap сначала помогает понять желаемый результат. Для неопределённой идеи важнее выяснить, для кого создаётся продукт и что пользователь должен уметь делать, чем сразу выбрать технологии и расположение файлов.

Обычно задаётся один основной вопрос за раз. Небольшой связанный набор допустим, когда помогает быстрее принять решение. Не требуется проходить одинаковую большую анкету для каждого проекта.

Пример: на сообщение «Хочу сайт для записи клиентов» разумно уточнить, кто записывает клиента и какой результат нужен на первом этапе. Выбор базы данных, платформы размещения и структуры кода становится полезным, когда ответы действительно влияют на него.

Затем согласуются нужные общие решения: назначение проекта, ваш способ участия, рабочие среды, доступы и хранение состояния. Git и работа на нескольких компьютерах обсуждаются только при реальной необходимости. Если часть решений пока открыта, она записывается как открытая, а не как уже принятая.

#### Если проект уже существует

Сначала система изучает доступные файлы, документацию, историю и другие относящиеся к работе источники. Она должна отличать то, что уже настроено, от того, чего пока нет или что требует проверки.

Если из файлов видно, как запускать тесты, не нужно просить пользователя вспомнить эту команду. Но из кода нельзя надёжно узнать, какой будущий вариант продукта вы предпочитаете: такой вопрос может потребовать вашего решения.

В ChatGPT загруженная копия помогает обсуждению. Когда требуется установить текущее состояние локального проекта, проверка должна выполняться в Codex или другой среде с подтверждённым доступом именно к нему.

Подключение существующего проекта не означает автоматической перестройки. Полезные планы, принятые решения и уже работающие инструменты должны использоваться повторно. Существенная смена общей организации требует отдельного основания.

## 2. Как Project Bootstrap организует работу

### 2.1. Manager, Master и Task

Три роли разделяют разные обязанности одной системы. После установки обычно оставляют включёнными все три компонента. Запросы вроде «Продолжим» или «Есть баг» должны направляться по смыслу; выбирать роль вручную перед каждым сообщением не требуется.

#### Manager — настройка общей работы

Manager помогает сформулировать цель и настроить способ работы над всем проектом. Он используется при начале нового проекта, подключении существующего, существенной перестройке, переносе или восстановлении общей организации.

Он выясняет важные решения, нужные среды, режим участия и разрешения. Если факт можно проверить в доступных материалах, Manager не должен заменять проверку вопросом к пользователю. Если материал недоступен, он должен объяснить, что нужно получить, и подготовить работу в подходящей среде.

Manager не обязан выполнять всю реализацию. Его задача — подготовить понятное продолжение работы, сохранив принятые решения и ограничения. Файл `CHATGPT_CLOUD_MANAGER.md` доставляет эти инструкции в ChatGPT; это не дополнительная четвёртая роль.

#### Master — координация рабочего проекта

Master работает там, где доступны реальные файлы проекта. Он читает сохранённое состояние, проверяет изменяемые сведения, определяет следующие шаги, организует выполнение и принимает результаты.

Перед доверием старой записи Master должен проверить относящееся к следующему действию состояние. Если файлы изменились после прошлого чата, актуальную картину нельзя получить только из истории разговора.

Небольшую локальную работу Master может выполнить сам. Отдельная Task нужна, когда полезно выделить конкретную работу со своими границами, ответственностью или состоянием для продолжения. Это решение не должно создавать новый чат автоматически.

#### Task — выполнение конкретной работы

Task занимается одной логической задачей: реализацией функции, исследованием, исправлением ошибки, проверкой или восстановлением незавершённой работы.

Ей нужны понятные цель, область, разрешённые действия, ограничения и признаки готовности. Например: «Выяснить причину ошибки сохранения в этой форме, ничего не исправлять, вернуть объяснение и результаты проверки».

Task не должна самовольно менять общую архитектуру, затрагивать область другой задачи или расширять разрешения. Одну логическую задачу в каждый момент изменяет один ответственный исполнитель. Читать результаты соседней работы можно в разрешённых границах; это не делает второго помощника параллельным владельцем изменений.

Общие принятые правила проекта не требуется заново переписывать в каждое сообщение задачи. Если исполнитель видит их в рабочем проекте, достаточно ссылки и сведений, которые относятся именно к текущей работе. Особое ограничение этой задачи при этом передаётся явно.

При переходе между средами или риске разных версий полезно указать, какая редакция правил применима. Если источник недоступен исполнителю, включается необходимая часть, а не вся история проекта. Это уменьшает дублирование, сохраняя понятные границы работы.

Каждая отдельная Task возвращает полезный результат координатору. Отсутствие отдельного файла передачи не делает короткий результат менее пригодным для проверки.

### 2.2. Сколько решений обсуждать с вами

Режим участия определяет, как часто вы хотите подключаться к работе над проектом:

| Режим | Поведение | Когда выбрать |
| --- | --- | --- |
| **Совместно** | Чаще показывает существенные варианты, находки и последствия. | Хотите участвовать в устройстве проекта и понимать выбор решений. |
| **По ключевым решениям** | Делает рутину самостоятельно, обращается на важных развилках. | Нужен разумный вариант по умолчанию без лишней переписки. |
| **Делегированно** | Сам принимает безопасные обратимые решения в уже разрешённых границах. | Хотите делегировать детали и получать результаты. |

Можно сказать: «Обсуждай со мной ключевые решения, остальное делай самостоятельно». Если система предлагает выбрать режим, все три варианта должны быть объяснены обычными словами.

Обращение к пользователю оправдано, когда неизвестен существенный продуктовый выбор, нужен новый доступ, не хватает важной информации или действие выходит за согласованные границы. Уже принятые решения и разрешения должны учитываться без повторного запроса на тот же шаг.

Режим участия не расширяет технические права. Даже «Делегированно» не превращает разрешение читать файлы в разрешение менять их, а изменение файлов — в разрешение публиковать сайт. Это также не просьба отказаться от проверки качества.

### 2.3. Откуда система знает состояние проекта

Project Bootstrap должен отделять принятые решения, наблюдаемые факты и предположения. «Мы решили не менять сервер» — ограничение пользователя. «Сервер отвечает сейчас» — факт конкретной проверки. «Возможно, ошибка связана с сервером» — гипотеза.

Сохранение гипотезы в файл не делает её подтверждённым знанием. Важно, к чему относится утверждение, где и когда оно проверялось, какая версия исследовалась и каким источником оно подтверждается.

Пример: запись в Git показывает сохранённую историю, файл на диске — текущие изменения, а проверка сервера — состояние работающей системы. Для разных вопросов нужны разные источники. Нет правила, по которому Git всегда важнее документа или любой свежий ответ сервера важнее принятого требования.

Если нужны сведения о недоступных файлах, Git, базе данных или сервере, система не должна придумывать их. Она готовит подходящую проверку, а неизвестное обозначает честно. Доступность инструмента не подтверждает доступ к нужному проекту: подключение к другому хранилищу не заменяет проверку вашей папки.

В отчётах полезно различать проверенные факты, обоснованные предположения и то, что осталось неизвестным. Для проверки вывода можно спросить: «На чём это основано и относится ли проверка к текущему состоянию?»

### 2.4. Маленькие и большие задачи

Маленькая работа обычно требует короткой последовательности: разобраться в нужном состоянии, выполнить разрешённое действие, проверить результат и сверить его с целью. Пример — исправить опечатку в документе или проверить один известный параметр.

Для такой работы могут не понадобиться отдельная Task, новый чат, длинный план, ветка Git или файл передачи. Само наличие инструмента планирования не означает, что его следует запускать.

Больше организации полезно, когда работа длинная, затрагивает разные части проекта, содержит рискованные решения, может оборваться или её контекст трудно восстановить. Тогда система фиксирует промежуточное состояние, план и результаты проверок. Глубина процесса зависит от сложности, риска и необходимости продолжения.

Одна логическая задача может выполняться в нескольких чатах. И наоборот, в одном чате можно выполнить несколько небольших задач. Внутреннее название логической задачи — **Task Branch**, конкретного сеанса работы — **Session**. Это не то же самое, что ветка Git: ветка нужна только для технического отделения изменений.

## 3. ChatGPT, Codex и передача работы

### 3.1. Переход из ChatGPT в Codex

Переход нужен, когда следующий согласованный шаг требует доступа к реальному рабочему проекту. Если достаточно обсуждения, оставаться в ChatGPT нормально.

Project Bootstrap готовит сообщение для Codex с нужным контекстом, целью, ограничениями, разрешёнными действиями и ожидаемым результатом. Работу с вашим локальным проектом обычно следует направлять сразу в Codex. Другая среда подходит, если известно, что она действительно видит именно эти файлы и может выполнить нужную проверку.

1. Откройте в Codex папку своего проекта, над которым хотите работать.
2. Скопируйте подготовленное сообщение целиком и отправьте его в Codex.
3. Дождитесь проверки или работы и отчёта.
4. Если обсуждение продолжается в ChatGPT, верните туда отчёт. Если управление работой уже перешло в Codex, продолжайте в рабочем проекте.

Если нужный проект не найден или открытая папка не подтверждена, Project Bootstrap должен остановить расширение поиска и попросить открыть или указать правильную папку. Самостоятельно искать по всему диску, домашней папке или произвольным родительским каталогам он не должен.

**Если Project Bootstrap установлен в Codex**, установленный плагин получает согласованный контекст и продолжает работу через свои обычные компоненты. **Если плагина нет**, сообщение описывает конкретную согласованную проверку или задачу без обязательного копирования всей системы. Если установка неизвестна, её сначала проверяют либо используют вариант для работы без плагина.

Когда сообщение действительно готово к передаче, сначала показывается весь текст для копирования, затем — отдельная рекомендация модели и уровня рассуждения, короткая причина и остальные комментарии. Совет о модели не входит в копируемое сообщение. Существенное нерешённое ограничение объясняется до объявления сообщения готовым.

Просьба «Объясни отчёт» сама по себе не является просьбой передать работу. В таком случае сначала нужен понятный ответ; готовое сообщение можно предложить для следующего реального шага.

После возврата отчёта ChatGPT объясняет, что подтверждено, что сделано, что осталось открытым и совпадает ли результат с целью. Английский отчёт не должен менять язык объяснения для вас.

### 3.2. Как сохраняется согласованная текущая работа

При переходе между ChatGPT и Codex система должна различать два случая.

#### Конкретная работа уже согласована

Например, договорились:

> Только выясни, почему падает тест X. Ничего не меняй. Нужен отчёт с причиной и подтверждающей проверкой.

В сообщение для Codex должны попасть цель, включённая область, явные исключения, разрешения и ожидаемый результат. В установленном Project Bootstrap для этого есть необязательный раздел **CURRENT ACCEPTED WORK** существующего сообщения Manager → Master. Это внутренний способ сохранить договорённость. Пользователю не требуется знать формат или вручную заполнять этот раздел.

Master сначала проверяет реальные файлы, затем выполняет или организует именно принятую работу. Частное ограничение «ничего не менять» сохраняется, даже если в общих правилах проекта ранее было разрешено изменение файлов.

Если файл X переименован в Y, Master может найти и проверить Y, когда это всё ещё та же цель и область. Новые факты меняют технический способ выполнения. Они не дают автоматического разрешения исправлять ошибку, расширять проверку на несвязанную область или заменять задачу другой.

Если прежних границ недостаточно, система объясняет конкретное препятствие. Когда отсутствует доступ, она просит предоставить его; когда нужен выбор пользователя — объясняет варианты; когда требуется расширить область или разрешённые действия — получает соответствующее решение. Если прежняя задача стала технически невозможна, она сообщает об этом и обсуждает дальнейший шаг. Например: «Для проверки требуется запуск сервера, а доступ не предоставлен». Подменять результат выполнением соседней задачи нельзя.

#### Конкретного следующего действия ещё нет

Можно просто передать уже обсуждённый проект в Codex. В этом случае конкретную Task не нужно придумывать ради заполнения сообщения. Передаются состояние проекта и принятые общие решения; Master проверяет реальные ресурсы и определяет следующий минимально необходимый шаг в имеющихся разрешениях.

Сведения о незавершённой работе помогают продолжению, но не заменяют явную передачу уже принятой текущей задачи. Если нужно сохранить определённую договорённость, её цель и ограничения должны быть понятны из самого сообщения.

## 4. Состояние проекта и продолжение работы

### 4.1. Что сохраняется для продолжения

Сохраняется то, без чего следующий помощник не сможет надёжно продолжить работу: цель, ограничения, принятые и открытые решения, выполненные шаги, частичные изменения, актуальные проблемы, результаты проверок и следующий шаг.

Например, для долгой задачи по авторизации полезно знать, какие способы входа согласованы, что уже реализовано, какие тесты запускались, что осталось и что запрещено менять. Пересказ всех сообщений с начала проекта обычно не нужен.

Состояние может храниться в проектных файлах, существующей системе учёта задач, согласованных документах или другом подходящем месте. Нет одного обязательного «магического» файла, который всегда подтверждает все сведения. Отсутствие специальной записи Task State не доказывает, что незавершённой работы нет.

Записи обновляются на значимых переходах, а не после каждого сообщения. Старую проверку нужно отличать от проверки текущей версии. Новая сессия использует записи вместе с фактическим состоянием ресурсов.

Если в ChatGPT накопились важные решения, которые должны пережить смену чата, а подходящего состояния в рабочем проекте ещё нет, может понадобиться компактная временная запись. Для короткого обсуждения она лишняя. После переноса решений в рабочий проект временная запись не должна становиться конкурирующим источником.

### 4.2. Результат задачи, Checkpoint и Handoff

У системы есть разные способы сообщить результат и сохранить работу. Сначала важно понять назначение; названия нужны лишь если вы увидите их в отчёте.

| Ситуация | Что достаточно подготовить | Внутреннее название |
| --- | --- | --- |
| Короткая задача завершена | Обычный ответ: результат, изменения, проверки, ограничения и открытые вопросы. | Task result. |
| Долгая задача ещё идёт | Актуальная запись цели, прогресса, текущего состояния и следующего шага. | Task State. |
| Незавершённая работа должна пережить окончание текущего чата | Сохранение сделанного, частичных изменений, проверок, проблем и способа продолжить. | Checkpoint. |
| Завершённый результат нужно сохранить для другой сессии, роли или среды | Отдельная передача результата с проверками и известными ограничениями. | Handoff. |

Для короткой задачи обычный ответ является полноценным результатом для проверки. Завершение само по себе не требует отдельного Handoff; короткий ответ не следует переименовывать в него. Закрытие чата также не означает, что работа закончена.

Checkpoint, напротив, сообщает: задача ещё не завершена, но её можно продолжить. Например: «Форма реализована, тест перезапуска ещё не выполнен, файлы изменены, следующий шаг — проверить восстановление данных». Пользователь не обязан вручную заполнять такой шаблон.

Долгая или трудная для восстановления работа может потребовать отдельного плана — **ExecPlan**. Он нужен для организации выполнения и продолжения, а не как обязательный документ любой правки.

Ни обычный отчёт, ни файл передачи сами по себе не публикуют изменения, не создают commit и не делают вывод автоматически принятым знанием всего проекта. Результат сначала рассматривается в пределах его цели и подтверждений.

### 4.3. Продолжение после паузы или обрыва

#### Обычная пауза

Если работа закончилась на понятном шаге, текущая сессия сохранилась и нет причин ожидать изменений извне, достаточно продолжить. Не нужен полный аудит после каждого перерыва или ограничения использования.

> Продолжим вчерашнюю задачу по авторизации.

#### Обрыв во время изменения файлов

Если команда, инструмент или соединение оборвались во время записи, результат мог быть частичным. Перед следующими изменениями нужно проверить, что реально успело произойти, какие файлы изменены и безопасно ли повторять действие.

> Работа оборвалась во время изменений. Сначала проверь фактическое состояние и только потом продолжай.

Система не должна повторять запись только потому, что в старом чате нет сообщения об успехе. Но и считать её завершённой без проверки нельзя.

#### Новый чат или изменившийся проект

Новая сессия восстанавливает цель и состояние из доступных записей, файлов и проверок. Если параллельно работал другой исполнитель или изменился сервер, обновляются именно те факты, которые нужны для следующего действия.

Цель восстановления — продолжить логическую работу, а не вспомнить старый разговор слово в слово. Если неизвестно, где произошёл обрыв, выбирается минимальная безопасная проверка, которая позволит действовать дальше.

### 4.4. Новый чат и доступ к сохранённому состоянию

Новый чат получает состояние из конкретного доступного источника: файлов рабочего проекта, источников ChatGPT Project или предоставленного документа. Нужно открыть нужный проект или дать чату материал и указать, где искать принятые решения и состояние работы.

Например, во время создания сайта вы решили, что клиентов записывает администратор и действующий сервер пока нельзя менять:

1. Project Bootstrap сохранил решения в согласованном документе проекта и указал его расположение.
2. Вы начинаете новый чат и просите продолжить работу по этому документу.
3. Если чат имеет доступ к источнику — например, документ находится в открытой папке Codex или добавлен в источники ChatGPT Project — помощник читает его и сверяет нужные текущие факты.
4. Если материал недоступен, помощник честно сообщает об этом, просит предоставить его либо направляет чтение в среду с доступом к нему. До получения материала он не должен считать решения восстановленными.

`CHATGPT_CLOUD_MANAGER.md` содержит инструкции самого Project Bootstrap. Он не хранит автоматически решения вашего конкретного проекта. Повторное прикрепление этого файла подключает правила работы; для продолжения нужны и относящиеся к проекту записи.

Пользователь не обязан вручную создавать Checkpoint перед каждым закрытием чата. Система сохраняет нужное состояние по необходимости; при продолжении важно, чтобы новый чат мог получить эту запись.

## 5. Проверка и приёмка

### 5.1. Две проверки готовности

Project Bootstrap проверяет две разные вещи:

1. **Работает ли сделанное так, как заявлено?** Например, форма сохраняет данные и соответствующий тест проходит.
2. **Выполнена ли исходная задача целиком?** Например, кроме сохранения требовалось восстановление после перезапуска, а его ещё не сделали.

Все запущенные тесты могут проходить, хотя одно требование пользователя вообще осталось вне реализации. Поэтому успешный тест не заменяет сравнение результата с принятой целью.

Во внутренних правилах проверка работоспособности называется **Verification**, а сверка полной цели — **Convergence**. В обычном объяснении достаточно сказать, что работает и что ещё не выполнено.

В отчёте должны быть фактически выполненные проверки, их результат и пределы. «Не проверено» означает, что проверка не запускалась; это не успех и не обязательно ошибка. Если есть известное ограничение, его сохраняют явно, чтобы координатор или пользователь мог принять решение.

Исторический результат относится к проверенной тогда версии. Для утверждения о текущей готовности нужны подходящие актуальные подтверждения. Если сервер недоступен, система не должна объявлять серверный сценарий успешным только по локальному тесту.

### 5.2. Как исправляются баги

Работа с ошибкой начинается с понимания исходного симптома. Нужно подтвердить его настолько, насколько позволяют доступ и воспроизводимость, собрать факты и отличить причину от предположения.

После разрешённого исправления повторно проверяется именно исходная проблема или максимально близкий валидный пример. Затем результат сравнивается со всей задачей: не остался ли другой обязательный сценарий.

Пример: после сохранения сбрасывается выбранный язык. Новый тест функции сохранения может пройти, но если сброс возникает только после повторного открытия формы, нужно проверить и этот путь. Переименование теста или проверка несвязанной части не подтверждают устранение пользовательской ошибки.

Если задача была «только выяснить причину», исправление не выполняется автоматически. Результат исследования — объяснение, подтверждающие сведения и то, что осталось неизвестным. Если воспроизвести проблему не удалось, это честно указывается вместе с фактически проверенными условиями.

### 5.3. Как координатор принимает результат

Master сначала изучает весь доступный результат и нужные подтверждения, затем решает, достаточно ли их для исходной цели. Готовые файлы и отчёты используются напрямую: исполнитель не должен пересказывать их заново ради формальности.

Все уже видимые пробелы по возможности собираются в один запрос доработки. Если потом появились новые данные, препятствие или потребность в проверке, может понадобиться новый цикл. Если координатор сам пропустил видимый пробел, его всё равно исправляют: сокращение переписки не важнее корректности.

Небольшую недостающую проверку Master может выполнить сам, когда у него есть актуальный доступ, действие уже разрешено, безопасно и тривиально, не требует реализации и не нарушает правило одного ответственного исполнителя. Более существенная работа направляется в подходящую задачу или требует вашего решения.

Например, проверить наличие уже созданного файла может быть проще напрямую. Исправление обнаруженной ошибки — отдельная работа, даже если её заметили при приёмке.

## 6. Разрешения, Git и рабочие среды

### 6.1. Разрешения и технические возможности

Возможность инструмента выполнить действие не означает разрешения пользователя. Важно не только само действие, но и ресурс, среда и ограничения: можно иметь право менять тестовую копию сайта и не иметь права менять действующий сайт.

| Действие | Что означает | Чего не разрешает автоматически |
| --- | --- | --- |
| Читать | Изучать разрешённые файлы и состояние. | Менять найденную ошибку. |
| Менять | Вносить изменения в согласованную область. | Сохранять их отдельным commit или отправлять наружу. |
| Создавать commit | Записать изменения в локальную историю Git. | Отправлять их в GitHub. |
| Публиковать, в том числе push | Отправлять изменения в удалённую систему в разрешённых границах. | Объединять их с общей веткой или развёртывать действующий сервис без соответствующего разрешения. |
| Интегрировать | Объединять результат с общей работой, например слиянием веток. | Другие внешние действия за пределами принятого разрешения. |

Пример: «Исправь локальную форму, но ничего не отправляй в GitHub» разрешает нужное изменение файлов. Наличие ключа GitHub не отменяет запрета на отправку. «Только проверь» остаётся ограничением даже при общих правах на изменение проекта.

Система должна использовать уже предоставленные разрешения, а не спрашивать повторно о каждом обратимом шаге внутри них. Новое подтверждение нужно при реальном выходе за границы, существенном риске или нерешённом выборе. Режим «Делегированно» этого разделения не меняет.

### 6.2. Git: локальная работа и GitHub

Git необязателен. Он полезен для истории изменений, совместной работы и отделения разных изменений, когда это требуется проекту.

Локальные файлы, локальная история Git и удалённый репозиторий GitHub — разные состояния. Изменённый файл может ещё не входить в commit; локальный commit может ещё не быть отправлен на сервер. Подключённый сервис также не доказывает, что на компьютере настроена нужная авторизация.

Project Bootstrap должен проверять соответствующее состояние и учитывать разрешения отдельно для чтения, изменения, commit, публикации и интеграции. Например, чистое состояние Git не доказывает, что весь запрошенный функционал реализован.

Отдельная ветка или рабочая копия Git нужна, когда полезно отделить изменения от параллельной работы или другого состояния проекта. Копия, связанная с тем же репозиторием, называется **worktree**. Создавать её для каждой маленькой задачи не требуется.

Внутреннее название логической задачи Task Branch не означает обязательной ветки Git. Не требуется выбирать сложную схему Git до того, как появилась причина её использовать.

### 6.3. Несколько рабочих сред

Для некоторых проектов важно различать несколько мест работы: папку на вашем компьютере, второй компьютер, общую папку, тестовый сервер, действующий сайт или внешний сервис. Система должна понимать, что где доступно и какие действия разрешены.

Например:

| Среда | Что нужно знать для работы |
| --- | --- |
| Локальная папка | Какие файлы открыты и что изменено. |
| Тестовый сервер | Доступен ли он и какую версию проверяют. |
| Действующий сайт | Какие действия разрешены и что нельзя затрагивать. |

Такая запись во внутренних правилах называется **Environment Map**. Это опора для координации, а не большая таблица, которую каждый пользователь обязан вручную заполнить. Записываются только среды, которые реально влияют на работу.

Сведения о доступности и состоянии меняются, поэтому их нужно обновлять подходящей проверкой. Принятое ограничение «не трогать действующий сайт» при этом сохраняет силу. Смена рабочей среды не расширяет разрешения сама по себе.

### 6.4. Продолжение на другом компьютере

Можно сказать:

> Хочу продолжить этот проект на домашнем компьютере. Проверь, что для этого нужно.

Project Bootstrap выясняет, доступны ли там актуальные файлы, сохранённые решения, состояние незавершённой работы и нужные сервисы. Он не предполагает, что достаточно перенести всю историю чата или только репозиторий, если важные материалы находятся отдельно.

Работу можно продолжать через общую папку, Git, отдельное хранилище знаний, внешний сервис или сочетание этих способов. Важен доступ к нужному состоянию, а не конкретный носитель. Внутреннее обозначение такого продолжения между средами — **PORTABLE**; оно не означает обязательной работы с флешкой.

Пример: код находится в Git, а незавершённые решения — в согласованном документе. На новом компьютере нужны оба источника. Если некоторые изменения остались только в старой рабочей папке, новая сессия не должна объявлять их уже доступными.

Если перенос между средами не нужен, отдельный процесс переносимости не создаётся. Если выбранный способ по-прежнему подходит, его используют повторно, проверив актуальную доступность.

### 6.5. Когда нужен перенос проекта

Открытие тех же файлов на другом компьютере обычно является продолжением работы. Смена локального пути или названия подключённого диска сама по себе не означает перестройку хранения проекта.

Настоящий перенос нужен, когда меняется основное место хранения или схема доступа: есть источник, назначение и необходимость подтвердить, что проект теперь можно надёжно продолжать в новом месте. Во внутренних правилах это называется **Migration**.

Тогда полезны подготовка источника, получение материалов в назначении и проверка нового состояния перед продолжением. Нужно понять, где теперь находятся актуальные файлы и решения, что перенесено, что осталось и какие ограничения действуют.

Например, переезд из личной папки в общее хранилище может изменить доступы и способ координации. Такие решения не следует подменять обычным «продолжим» без проверки. Но создавать документы переноса при каждом изменении пути также не требуется.

### 6.6. Пароли, ключи и доступ к сервисам

Вопрос хранения данных доступа возникает, когда перенос между средами действительно нужен, работа зависит от сервиса с авторизацией, доступ влияет на следующий шаг и подходящего согласованного решения ещё нет.

Если ранее принятый способ работает, достаточно проверить доступ. Не нужно заново обсуждать хранение ключей при каждой передаче работы. Существенная смена среды, нового сервиса, доступности, риска или разрешений может потребовать пересмотра.

В текущей версии предусмотрены два подхода:

1. Настраивать данные доступа отдельно на каждом компьютере.
2. Хранить их вместе с переносимой рабочей средой, но вне Git.

Выбор не должен автоматически сводиться к первому варианту. Режим участия определяет, требуется ли ваше явное решение или допустим безопасный обратимый выбор в уже разрешённых границах. Конкретные программы хранения обсуждаются, когда они действительно понадобятся. Project Bootstrap не задаёт в этой версии универсальную систему зашифрованного хранилища.

Значения паролей, токенов, закрытых ключей и ссылок с секретами не сохраняются в проектных записях, сообщениях передачи, журналах или Git. Сохранять можно только несекретные сведения: есть ли доступ, какой способ принят, где искать механизм доступа без раскрытия значения и как восстановить или отозвать доступ.

Наличие авторизации не заменяет разрешения на действие. Доступ к GitHub может понадобиться для чтения, но это не даёт права автоматически публиковать изменения.

## 7. Дополнительные возможности

### 7.1. Другие навыки, плагины и методики

Project Bootstrap может использовать дополнительный навык, плагин или инструмент для полезного этапа — например, проверки, подготовки документа или уточнения требований. Сначала определяется цель и нужная глубина процесса, затем выбирается подходящее средство.

Наличие инструмента не означает обязательного запуска всего его процесса. Если нужен один этап проверки, не требуется создавать заново спецификацию, план и новую цепочку согласований только потому, что они предусмотрены внешней методикой.

Уже существующие планы, требования, результаты и записи задачи должны использоваться повторно. Перед запуском выбранного этапа проверяется, есть ли нужные исходные материалы и технические условия. Предсказуемую ошибку запуска не следует использовать вместо такой проверки.

Если не хватает существенного предварительного этапа, его нельзя незаметно добавить к вашей задаче. Система объясняет, что именно нужно, и спрашивает только о реальном выборе, разрешении или границе работы. Простой технический шаг в уже разрешённых границах не должен становиться лишней церемонией.

Пока Project Bootstrap координирует проект, дополнительный инструмент выполняет выбранный этап, а его результат рассматривается как подтверждение для дальнейшей работы. Не должно быть двух параллельных систем, каждая из которых пытается руководить одной задачей.

Если вы явно поручили другой системе весь процесс, Project Bootstrap не создаёт дублирующую цепочку поверх него. Если поручен только один этап, остальные шаги остаются под прежней координацией. В обоих случаях сохраняются границы проекта, разрешения и требования к проверке.

### 7.2. Модель и уровень рассуждения

При подготовке передачи работы в Codex Project Bootstrap даёт рекомендацию конкретной модели и уровня рассуждения, если вы не отказались от таких советов. Рекомендация помогает подобрать достаточную способность для задачи без автоматического выбора самого дорогого или высокого варианта.

Модель и уровень выбираются отдельно. Более сильная модель не требует высокого уровня для любого действия. Простое чтение файла, обычная реализация и сложное восстановление после конфликтующих изменений требуют разного усилия.

Ориентиры для понимания рекомендации:

| Уровень | Типичная причина выбора |
| --- | --- |
| Низкое | Механическое чтение, извлечение сведений, небольшая однозначная проверка. |
| Среднее | Обычная реализация, локальная отладка или ограниченный разбор. |
| Высокое | Сложная ошибка, архитектура, восстановление, противоречивые данные или трудная проверка. |
| Очень высокое / Максимальное | Исключительно сложная работа с отдельным обоснованием и поддержкой выбранной моделью. |

Рекомендация опирается на актуальные сведения именно о Codex и на ваши реальные возможности. Старый пример или общие сведения о ChatGPT не подтверждают, что модель доступна вам в Codex или лучше подходит для текущей работы.

Если применимого набора рекомендаций ещё нет, система один раз проверяет надёжные текущие данные и формирует компактный набор для трёх–пяти типов работы. Это соответствие «тип работы → конкретная модель → поддерживаемый уровень рассуждения», при необходимости с более сильным уровнем для трудных случаев. Например, отдельно рассматриваются простые проверки, обычная реализация и сложная отладка. Одна модель может подходить нескольким типам работы. Пользователь не обязан заранее составлять этот набор.

Сначала устанавливается актуальная основная линейка моделей. Старая поддерживаемая модель не становится обычным выбором только потому, что существует. Для её предпочтения нужно конкретное основание: ограничения реально доступных вам вариантов, недоступность актуальной основной модели или подтверждённое преимущество для данного типа работы.

После формирования или обновления система один раз показывает принятый компактный набор рекомендаций пользователю. При передаче он размещается после готового сообщения, конкретного совета и короткой причины, вне текста для копирования. Затем применимые рекомендации используются повторно.

Если реальные доступные вам модели в Codex ещё неизвестны, после первого общего набора и первой пригодной рекомендации система должна **один раз предложить сообщить доступные варианты** — например, список или снимок переключателя моделей. Само предложение обязательно; отвечать на него необязательно, и оно не блокирует передачу работы. Если варианты уже известны, приглашение повторять не нужно. Ваш ответ уточняет или заменяет общие рекомендации; дальше используются реально доступные варианты.

Очередная передача, новый запрос, усложнение одной задачи или прошедшее время сами по себе не запускают новое исследование моделей. Для более сложной задачи выбираются подходящие модель и достаточный поддерживаемый уровень из принятого набора.

Пересмотр нужен при конкретном изменении: рекомендованная модель недоступна; получен ваш список или снимок переключателя; сообщено о новых моделях; вы прямо попросили обновить рекомендации; назначение работы изменилось с Codex на другую среду; либо есть другое конкретное подтверждение, что прежний набор неприменим. Новые сведения о доступности могут потребовать повторного уточнения вариантов. Сообщение о новой модели приводит к одной ограниченной проверке, а не к выдумыванию её возможностей.

Название модели показывается точно, уровень — на языке общения, с короткой причиной. Рекомендация остаётся вне сообщения для копирования. Можно сказать: «Не рекомендуй модели»; советы, включая приглашение уточнить варианты, прекращаются до отмены этой просьбы, а передача работы остаётся доступной.

Если после ограниченной проверки актуальных данных и полезных уточнений надёжный конкретный совет установить не удалось, используется метка **«Конкретная модель не подтверждена»** с объяснением неопределённости. Неизвестный переключатель сам по себе не требует этой метки: сначала может использоваться общий подтверждённый набор. Недостаток подтверждений для рекомендации не означает, что программа не установлена. Система не должна заменять неизвестное выдуманным названием.

### 7.3. Язык общения

Объяснения, вопросы, обсуждение вариантов, выводы и интерпретация результатов остаются на вашем языке. Видимое общение меняется по вашей просьбе, а не из-за загруженного файла или английского отчёта.

Внутренние инструкции и сообщения между помощниками могут быть на английском. Это допустимо для устойчивого выполнения, но окружающее объяснение для вас должно оставаться понятным.

Техническое слово из чужого отчёта, готового сообщения или журнала не доказывает, что вы сами им владеете. Система сначала объясняет смысл обычными словами и только при пользе добавляет внутренний термин. Для начала работы не требуется выбирать свой «технический уровень».

Можно сказать: «Объясни проще» или «Что означает этот термин?» Последующие ответы тоже должны стать проще. Предпочтения общения можно сохранять, когда вы сами выразили или приняли их; предположение помощника о ваших знаниях не заменяет такого основания.

## 8. Практическое использование

### 8.1. Типовые сценарии

#### Создать новый проект

> Хочу сделать сайт для записи клиентов. Помоги начать.

Сначала уточняются цель и важные решения. Технологии не выбираются раньше, чем они влияют на понятный результат. Когда понадобятся файлы и команды, работа направляется в доступную рабочую среду.

#### Подключить существующий проект

> Подключи Project Bootstrap. Сначала изучи текущие файлы и скажи, что уже настроено.

Система использует имеющиеся материалы и проверяет текущие факты. Она не должна повторять анкету там, где ответы уже доступны, или перестраивать проект без основания.

#### Продолжить работу

> Продолжим вчерашнюю задачу по авторизации.

Используются сохранённые решения и состояние задачи. Изменяемые сведения обновляются настолько, насколько это нужно следующему действию; не требуется пересказывать весь старый чат.

#### Добавить функцию

> Добавь возможность отменять запись за сутки. Остальную логику не меняй.

Уточняется только необходимое для результата. Размер процесса соответствует сложности. Ограничение на остальные части сохраняется при выполнении и проверке.

#### Исправить баг

> После сохранения иногда исчезает выбранный язык. Разберись и исправь.

Подтверждается симптом, исследуется причина, выполняется разрешённое исправление и проверяется исходный сценарий. Предположение не выдаётся за установленную причину.

#### Продолжить после обрыва

> Команда оборвалась во время изменения файлов. Проверь, что успело измениться, и продолжим.

Перед новой записью проверяется фактический результат. Частично выполненный шаг не должен ни повторяться вслепую, ни считаться завершённым без подтверждения.

#### Открыть на другом компьютере

> Хочу продолжить дома. Проверь, доступны ли нужные материалы и сервисы.

Система проверяет состояние и доступность принятого способа продолжения. Смена компьютера не означает обязательного переноса хранения или экспорта всех чатов.

#### Проверить готовность

> Проверь, всё ли готово по исходной задаче, включая восстановление данных после перезапуска.

Проверяется работа результата и полнота требований. Успешные тесты не скрывают невыполненный пункт или незапущенную проверку.

#### Передать из ChatGPT в Codex

> Подготовь сообщение для Codex: только выяснить причину падения теста X, ничего не менять.

Передаются именно исследование, его область, запрет изменений и ожидаемый отчёт. Переименование файла может изменить способ поиска, но не разрешить исправление или несвязанную работу.

### 8.2. Если Project Bootstrap ведёт себя неправильно

| Проблема | Что можно написать | Какого поведения ожидать |
| --- | --- | --- |
| Спрашивает о фактах, которые уже есть в файлах | «Сначала изучи доступные материалы. Спрашивай о том, чего там нет». | Использование доступных подтверждений вместо повторной анкеты. |
| Создаёт слишком много процесса | «Используй самый простой достаточный процесс для этой задачи». | Только необходимые этапы и записи; для маленькой работы возможен прямой результат. |
| Не находит нужный проект в открытой папке | «Попроси открыть или указать правильную папку». | Уточнение папки с остановкой расширения поиска; поиск по всему диску не начинается. |
| Угадывает состояние недоступных файлов | «Проверь это в Codex. Не считай предположение фактом». | Проверка в нужной среде либо честное указание неизвестного. |
| Потерял ограничение после перехода | «Мы согласовали только проверку без изменений. Сохрани эту цель и ограничения». | Возврат к принятой работе; новая область или исправление не разрешаются автоматически. |
| Просит пересказать доступный результат | «Прочитай готовый отчёт и собери все уже видимые пробелы в один запрос». | Полный просмотр результата без лишнего пересказа. |
| Повторяет действие после обрыва | «Сначала проверь, что реально успело выполниться». | Установление фактического состояния перед следующими изменениями. |
| Объявляет готовность только по тестам | «Сверь результат со всеми исходными требованиями». | Проверка и работоспособности, и полноты задачи. |
| Снова исследует модели при каждой передаче | «Используй применимые уже принятые рекомендации; объясни, какие новые данные требуют пересмотра». | Повторное использование рекомендаций без исследования ради формальности. |
| Усложняет объяснение чужими терминами | «Объясни смысл обычными словами и дальше говори так же». | Понятные последующие ответы, без предположения о вашем техническом опыте. |

Если требуется пересмотреть общую организацию, скажите: «Нужно пересмотреть способ работы над всем проектом и объяснить варианты». Это отличается от выполнения одной конкретной задачи.

Для разбора неправильного поведения полезны исходный запрос, ответ системы, важное ограничение и фактически доступные ресурсы. Не включайте секреты. Один конкретный пример полезнее общего утверждения «всё работает неправильно».

### 8.3. Обновление и статус версии

#### Если источник добавлен через Codex CLI

В обычном терминале с установленным Codex CLI посмотрите настроенные источники:

```text
codex plugin marketplace list
```

Для источника Project Bootstrap выполните обновление по его техническому имени:

```text
codex plugin marketplace upgrade gipsy-project-bootstrap
```

Затем перезапустите приложение, откройте каталог плагинов и убедитесь, что Project Bootstrap остаётся установленным и включённым. Продолжайте в новом чате. При обновлении источника Codex может обновить установленную копию настроенного плагина.

#### Если используется скачанная локальная копия

Обновите ту папку репозитория, из которой подключали каталог: скачайте новую опубликованную копию с [GitHub](https://github.com/gipsy-teapsy/project-bootstrap) и замените файлы в этом расположении; если получили копию через Git, обновите её из того же источника. Важно обновить и каталог в корне, и папку плагина, на которую он указывает.

Откройте обновлённую папку как проект и полностью перезапустите приложение: по документированному механизму локальная установка подхватит новые файлы. Проверьте в каталоге, что Project Bootstrap включён, затем вернитесь в рабочий проект и начните новый чат. Порядок добавления и обновления источников описан в [официальной документации OpenAI](https://developers.openai.com/plugins/build/plugins).

#### Если плагин установлен в рабочем пространстве ChatGPT

Для установки через GitHub в рабочем пространстве ChatGPT порядок обновления указан в [инструкции установки](https://github.com/gipsy-teapsy/project-bootstrap/blob/main/docs/MARKETPLACE_INSTALL_RU.md).

#### Если используется файл в ChatGPT

Если работаете через файл в ChatGPT, замените старый `CHATGPT_CLOUD_MANAGER.md` файлом из новой опубликованной версии. В обычном чате прикрепите новый файл; в ChatGPT Project замените старый источник. Короткую инструкцию сверяйте с актуальным блоком Project Instructions: если он прежний, повторно вставлять его не требуется. Весь файл в поле инструкций копировать не нужно.

Не объединяйте вручную части разных версий. Полезно проверить номер версии и сведения об исходных инструкциях в новом готовом файле.

Версия 0.1.8 остаётся бета-версией. Есть результаты отдельных проверок поведения; более широкая проверка продолжается. Проверка структуры пакета не доказывает работу всех пользовательских сценариев.

Особенно полезно сохранять примеры лишних вопросов, повторной работы после обрыва, потери ограничений, неподтверждённой готовности и вынужденного изучения внутреннего жаргона. Они помогают проверить конкретную гипотезу о поведении системы.

## 9. Справочник терминов

### 9.1. Если в отчёте встретился внутренний термин

Для начала работы этот словарь не нужен. Он помогает читать подробный отчёт или сопоставить его с поведением системы.

| Термин | Смысл для пользователя |
| --- | --- |
| Task Branch | Одна логическая задача, которая может продолжаться в нескольких чатах; отдельная ветка Git из этого не следует. |
| Session | Конкретный чат или сеанс, выполняющий роль; сам проект и его важное состояние шире этого чата. |
| Task State | Сохранённое текущее состояние незавершённой работы. |
| Checkpoint | Запись для продолжения незавершённой работы после окончания текущего сеанса. |
| Handoff | Сохранённая передача завершённого результата при реальной необходимости продолжения между ролями, сеансами или средами. |
| Verification / Convergence | Проверка работоспособности / проверка достижения принятой цели целиком. |
| CURRENT ACCEPTED WORK | Уже согласованная конкретная работа, включённая в передачу проекта; при отсутствии такой договорённости раздел не нужен. |
| Environment Map | Запись значимых рабочих сред и доступных возможностей. |
| PORTABLE / Migration | Продолжение в разных средах / настоящий перенос основного хранения или схемы доступа. |
| ExecPlan | План длинной или трудной для восстановления работы, который не нужен каждой маленькой задаче. |

Для силы утверждений могут встречаться метки **CONFIRMED** — подтверждено в своей области; **OBSERVED** — непосредственно наблюдалось в определённой среде и времени; **STRONGLY SUPPORTED** — есть несколько согласующихся оснований, но не прямая проверка; **INFERRED** — вывод из имеющихся данных; **UNKNOWN** — данных недостаточно. Это обозначения достоверности, а не разрешения на действия. Сохранение записи не повышает её достоверность автоматически.
